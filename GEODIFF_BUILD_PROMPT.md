## 1. Product and audience

I am Abdul Hannan, a CS graduate building a portfolio for US GIS developer and geospatial application developer roles. I want a recruiter to understand the project in 30 seconds and a GIS engineer to find enough substance to discuss for 20 minutes.

GeoDiff helps one GIS analyst reconcile a field inventory with last month's approved inventory. Given two point datasets, it identifies additions, deletions, significant moves, and edited attributes. An analyst inspects the evidence, records decisions, and exports an inventory containing the approved updates. The app never writes to the original files or to the source ArcGIS service.

Use a fictional parks department in the Dallas area. The default story follows a park bench whose reported position moved to another block while its condition also changed. The analyst can accept the condition update and reject the move. Generate all demo assets and context locally, identify the data as synthetic, and give the named example a stable ID such as BENCH-0142. Measure the actual movement. Use that same record in the walkthrough, README, screenshots, and tests.

The public entry URL opens a populated, interactive review with that change selected. Put “Try your own files” and “Import public layer” within reach. A recruiter can review, download a result, and reset the demo without an account, API key, installation, or access to my computer.

## 3. What the engine must mean by a change

1. Accept two RFC 7946 GeoJSON FeatureCollections of 2D Point features in longitude/latitude WGS84. Offer a sample download. Show file name, feature count, candidate ID fields, field coverage, and validation problems before comparison. Reject unsupported geometry, null/invalid geometry, nonfinite or out-of-range coordinates, and declared conflicting CRS with actionable errors. Coordinate ranges alone cannot certify a CRS. Explain how to reproject other data in QGIS.
2. Let the reviewer choose the identifier field for each version and the attributes to compare. Reject null, empty, duplicate and ambiguous normalized IDs. Document ID policy including string vs numeric IDs and leading zeros. Never match by array position. Treat a changed ID as an addition and a deletion. Warn when the versions have very little ID overlap.
3. Retain the original uploads and their SHA-256 hashes in the local/private workspace. Store normalized copies. Document which fields are compared, ignored, and preserved. For v1 support scalar property values for comparison, distinguish absent from null and string from number, and preserve unselected and nested properties from the approved baseline. Exclude importer timestamps and chosen ID keys from change suggestions.
4. Store geometry as geometry(Point,4326). Calculate move distances in meters on the WGS84 spheroid, for example with PostGIS geography. Use full precision for classification and round for display. A move is reviewable when distance is strictly greater than the selected tolerance. Include tests for zero, small displacements, high latitude and longitude wraparound. Treat sub-threshold motion as unchanged in the reviewed export.
5. Additions/deletions are whole-feature decisions. Matched records can have a movement change plus one change per selected edited field. Group components under their asset. Counts explicitly distinguish affected assets, components, and pending decisions.
6. Each component has a pending, accepted, rejected, or flagged disposition. Flagging requires a note and leaves it unresolved. Accepted components apply the proposed value. Rejected and unresolved components retain the baseline. Accepting an addition inserts the new feature, accepting a deletion removes it. Rejecting either preserves baseline membership. Bulk decisions must describe the target count and scope. Allow a user to change their mind with an audit entry.
7. Final export requires all dispositions resolved. Provide a draft export at any time with unresolved changes separately identified in the report. Produce valid GeoJSON and a machine-readable audit/report with hashes, source attribution, threshold, units, compared fields, counts, decisions, comments and timestamps. Reimport the exported file in the test suite. Resolve to a deterministic order. Explain omission of the baseline feature when an addition is pending.
8. Treat a tolerance or field change as a new comparison run with its own decisions and lineage. Prompt before leaving a partially reviewed run, and retain the old run. Preserve data across reloads inside the active workspace.

## 4. Visual direction and interaction design

Design the interface as a **cartographer's proof sheet**. At a glance it should feel like an instrument for checking edits to a printed city atlas. Show what changed using overprinted symbols, registration marks, movement lines, and a paired evidence strip. Every graphic should help locate, compare or review a feature.

- Use warm paper (#F5F2E9), near-black ink (#202A2A), a subdued street grid, and restrained color. Pair deep teal with a plus for additions, rust with a crossed outline for removals, cobalt with an arrow for moves, and plum with a split square for attribute edits. Verify contrast in the rendered UI. Use shape, label and pattern in addition to color. Use a locally served humanist sans for controls and a mono face for IDs, coordinates and measured distances. Include license files for bundled fonts, or use system fonts.
- Desktop composition at 1440px: a slim toolbar with dataset names, review progress and export, a filterable queue roughly 270px wide, a flexible central map, and a 320–360px evidence panel. At medium widths make the panel a drawer. At phone widths use Map, Queue and Details tabs retaining the same selection, and a reachable decision bar. Test 390px, 768px and 1440px.
- The signature interaction: select BENCH-0142. Show the old point as an open ring, the proposed point as a filled mark, and a connecting line with direction and measured distance. Frame both points. In the evidence panel show field-level old and new values with separate decision controls, an audit trail and undo. A split or synchronized before/after view is an enhancement once the overlay works. Make overlapping points and unchanged-location attribute edits discoverable.
- The initial screen should show the map, a changed record, a readable explanation, and a clear next action above the fold. Use synthetic parks, paths and street blocks as bundled context. Keep MapLibre style resources local, including fonts/sprites if used. Preserve visible attribution for any sourced layers.
- Keep map and queue selection in sync. Expose keyboard navigation, visible focus, escape to close, reduced motion, and a fully usable table/inspector alternative if WebGL is unavailable. Scroll long lists efficiently and preserve focus after decisions. Explain what happened on loading, empty, invalid, offline, and export states. Use progress indicators only for measurable progress. Add a short optional guided tour and a direct link to the repository. Review the running interface at each breakpoint and fix clipped labels, unreadable popups and obscured controls.

## 5. Infrastructure, persistence and boundaries

Organize the repository around web/, api/, fixtures/, scripts/, docs/, .github/workflows/ and compose.yaml. Adapt to existing repo conventions. Implement the ArcGIS importer as a **curated source picker**. Resolve public HTTPS endpoints from server configuration, check the exact host/layer allowlist, and reject redirects outside the configured source. Read metadata, geometry type, query capability, field types, spatial reference, max record count and attribution. Request outSR=4326. Prefer GeoJSON when supported, otherwise normalize Esri point JSON explicitly. Request object IDs then query bounded batches, or paginate in a stable documented order. Compare expected and retrieved IDs, handle source changes or incomplete replies, and only commit a complete snapshot. Use retries with bounded backoff and a timeout. Snapshot the same source on demand; explain the distinction between a persistent asset ID/GlobalID and a server OBJECTID that can change after republishing. Offline mocked fixtures cover the importer in CI. Pick and verify at least one actual, reusable public point layer at implementation time. Never imply synthetic edits are real changes reported by a city.
